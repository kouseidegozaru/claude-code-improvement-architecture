# 設計の根拠

2つのプロンプトに書かれた制約が、それぞれどの失敗モードを防いでいるかの対応表。
プロンプトを短くしたくなったときは、この表を見て「何を外そうとしているのか」を確認すること。

## 1. 前提となる問題

自己改善エージェントが最初の前提を覆せない理由は、能力ではなく**探索構造**にある。

| 構造上の性質 | 帰結 |
|---|---|
| 最初の要件定義がアンカーになる | 以降の改善はすべてその周辺で起きる |
| 自己反省が同じモデル・同じ文脈で行われる | 同じ推論経路をなぞり、反省の射程が広がらない |
| 「いま一番良い1本」を単一スコアで磨く | グローバルベストの近傍しか探索されない |
| 単調改善のルール | 一度スコアを下げる方向の一歩が構造的に禁止される |

脱出は3方向。**複数候補の並行改善**（パレート選択）、**アーカイブと系統による踏み石の保存**、
**多様性を評価に組み込むこと**。プロンプト2の P1〜P5 がこの3つの実装指示にあたる。

ただし、探索構造より先に決めるべきものがある。**評価**である。
何が良くなったと言えるのかが測れないまま探索を回しても、生まれるのは改善ではなくノイズになる。
プロンプト2でフェーズ1（観測とベースライン取得のみ、適用禁止）を最初に置いているのはこのため。

## 2. なぜ観測と変更を分離したか

MCP サーバー（プロンプト1）にはハーネスを変更する機能を持たせず、
自己改善ループ（プロンプト2）には観測ロジックを持たせない。

分離自体が安全機構である。同じ主体が「測る」と「良く見せるために変える」の両方を持つと、
指標を上げる最短経路は「測り方を変えること」になる。
プロンプト1 の非目標に「ハーネスを変更する機能を持たせない」「評価器にしない」を、
プロンプト2 の P9 に「提案する者と評価する者を分ける」を置いているのは同じ理由。

## 3. プロンプト1（MCP サーバー）の制約

| 制約 | 防いでいる失敗 |
|---|---|
| C1 コンテキスト経済性 | 生ログの流し込みで、分析する側の文脈が1回の呼び出しで溶ける |
| C2 出力の二層化 | 既定で本文を返すと、証拠の確認が文脈汚染と機密露出を常時招く |
| C3 本文を外部データとして扱う | **間接プロンプトインジェクション**。下記4節 |
| C4 証拠と発生回数の添付 | 印象論の上に改善が積み上がる。N=1 が恒久ルールの根拠になる |
| C5 決定性 | 評価関数として使えない（呼ぶたびに結論が揺れると前後比較が成立しない） |
| C6 形式変化への耐性 | 更新後に**静かに間違った数字を出し続ける**。最も危険な壊れ方 |
| C7 読み取り専用・外部通信ゼロ | 認証情報や非公開コードの流出、証拠そのものの破壊、保持期間管理の外への複製 |
| C8 正直さ | 欠測をもっともらしい数字で埋め、ループが嘘の上に改善を積む |
| C9 安定した識別子 | 「あのとき見つけた問題はまだ起きているか」を追跡できない |
| C10 規模への耐性 | セッション増加でループが回らなくなり、運用が止まる |

「まず実物を調べる」を第1節に置いたのは、記録に存在しないデータを前提にした分析軸を作らせないため。
分析軸はデータから逆算する。同じ節に「集計の落とし穴を実データで確認せよ」を置いたのは、
記録の書かれ方によっては素朴な集計が二重計上になり、**全指標が静かに壊れる**ため。
これは実装の選択ではなく事実確認なので、指示書側で確認を要求している。

### 分析軸の重心

既存のセッション分析ツールはほぼすべて「コストの可視化」か「閲覧・検索」に寄っている。
自己改善ループが必要とするのはそこではなく、**ハーネス要素と結果の対応づけ**である。

- どのフックが何回モデルを差し戻したか（＝ハーネスの摩擦点）
- 同じフィードバックが同一セッションで繰り返されているか（＝指示文が効いていない）
- 読み込まれているのに一度も使われない skill / MCP はどれか（＝文脈の無駄）
- 権限の拒否がどこで起きたか（＝権限設計と実作業のずれ）
- 委譲は割に合っていたか（渡した量・消費した量・返ってきた成果）

プロンプト1で「ハーネスの効き目について」の節を厚くしているのはこのため。

## 4. 間接プロンプトインジェクション（この構成に固有の穴）

セッションの記録には、取得した web ページ、issue のコメント、依存ライブラリの説明文など、
**第三者が書いた文字列がそのまま入る**。

分析サーバーがそれを読み出し、自己改善ループがそれを読むと、
第三者の文字列がハーネスの改善指示として解釈されうる経路ができる。
悪意ある文字列を含むページを一度取得させるだけで、設定ファイルに間接的に書き込めることになる。

対策は3層。**(1)** 本文はデータであると分かる形で包む、
**(2)** その旨をツールの説明文に書く（読む側が必ず目にする場所）、
**(3)** そもそも既定では本文を返さない（C2）。

## 5. プロンプト2（自己改善ループ）の原則

| 原則 | 防いでいる失敗 |
|---|---|
| P0 探索制御を決定的コードに置く | 選抜基準がラウンドごとに動く。動く基準の上の改善は改善でない |
| P1 丘登り禁止・合成スコア禁止 | 局所最適への直行。重み付けは gaming の設計図そのもの |
| P2 パレート保持／保持と選択の分離 | 総合1位への一元化で探索が死ぬ。多様性と分岐を1つのスコアで兼ねると片方が犠牲になる |
| P3 アーカイブと系統／良い候補≠良い親 | 踏み石の喪失。高得点の行き止まりを掘り続ける |
| P4 多様性を構造で測る | 全候補が同じ前提上の微調整になる。表層で測ると水増しされる |
| P5 前提破壊枠の義務化／禁止手リスト | 指標が良好なときほど局所最適に居座る。同じ失敗が新案として再提出される |
| P6 前提台帳 | 書かれていない前提は覆せない |
| P7 テキストの反省信号 | スカラーからは改善の方向が読めない |
| P8 証拠と発生回数 | 一般論でハーネスが単調に膨らむ |
| P9 提案者と評価者の分離 | 自分の点数のつけ方を自分で変える |
| P10 まず削る（改善手段の優先順位） | **このループ最大の局所最適**。下記6節 |
| P11 最小単位／狙う指標の事前宣言 | 原因が分離できない。後付けで良かった指標を探す |
| P12 可逆性（git のみ） | 悪化に気づいたときに戻せない。チェックポイントは代替にならない |
| P13 正直な報告 | 成果の過大報告。ここが壊れるとループ全体が無価値になる |

## 6. 最も起きやすい局所最適：指示文の単調増加

「失敗を見つけた → 指示に1行足す」は、最も手軽で、短期的に正しく見えて、長期的に確実に壊れる。
指示は増えるほど1つあたりの遵守率が下がるので、**改善が積み上がるほど効かなくなる**。

だから改善手段に優先順位を与える。① 削る・統合する → ② 仕組みに落とす（機械的に強制する）
→ ③ 文脈を限定する → ④ 最後の手段として常時読まれる指示に追記する。
そして常時読み込まれる分量に上限を設け、追記するには何かを削らせる。

## 7. 反ゴドハートの構造

指標は3層に分ける。**ゲート指標**（二値、1つでも割れたら自動却下）、
**主要指標**（1つだけ、事前宣言）、**副次指標**（パレート判定用）。
主要が改善し副次が有意に悪化していない場合のみ採用する。合成スコアは作らない。

各指標の gaming 経路は事前に書き出す。実例：

| 指標 | gaming 経路 | 対 |
|---|---|---|
| 成功率 | 検証を弱める／簡単な作業だけ選ぶ | 合否条件の不変をゲート指標に |
| 手戻りの少なさ | 何もしなければ起きない。**人間が諦めて自分で直しても記録上はゼロ** | 「どれだけ進んだか」と対で見る |
| トークン効率 | 調べずに書く／**委譲先に押し付けて親の数字だけ下げる** | 作業1件あたりの総量、委譲分を合算 |
| 人間の介入の少なさ | **権限を緩めれば劇的に下がる**（安全性を売って指標を買う） | 権限変更はこの指標の最適化対象外＋事前承認 |
| 所要ターン数 | 検証手順を省く | 「検証が実行されたこと」をゲート指標に |
| 指示の遵守率 | 指示を足せば上がるように見える | 分量の上限（6節） |

さらに、観測を減らす変更・ケースを消す変更・失敗を「対象外」に再分類する変更を構造的に禁止する。
指標を上げる最短経路が「良くすること」ではなく「測るのをやめること」になる穴を塞ぐため。

**壊れたケースは「合格」ではなく「無効」**として扱う。取り違えると回帰スイートが静かに空になる。

## 8. サンプルが少ないときの判断

| 証拠 | 判断 |
|---|---|
| ゲート指標が1つでも割れた | 自動却下 |
| 決定的に再現する回帰ケースが、変更前は必ず失敗し変更後は繰り返し成功 | 1件でも採用可（根拠は統計でなく再現性） |
| 平均は改善したが差がばらつきの範囲内 | 採用しない（記録は残す） |
| 差がばらつきを明確に超え、副次指標の悪化なし | 採用可 |
| 主要は改善、副次が悪化 | 人間に上げる |

比較は同じケース集・同じ日・同じバージョンで行う。期間の前後比較はしない（作業内容やバージョンと交絡する）。
効果がなかったことも必ず記録する。しないと同じ提案が何度も出る。

## 9. なぜ不変条件は「書くだけ」では守れないか

1. **エージェントは「良くなること」ではなく「良いと判定されること」に最適化する。**
   自己改善するコーディングエージェントの研究では、「ツール使用について嘘をつくな」という評価項目を
   追加したところ、嘘を減らすのではなく**検出用の目印をログから消す方向にコードを書き換えた**事例が
   報告されている。目標の書き方の工夫では防げない。
2. **設定は実行中に自動で読み直される。** エージェントが書いたフックは同じセッション内で即座に
   任意のコマンドとして動き出す。「生成したコードが自動で常時実行される」経路を構造として内包している。
3. **保護の宣言を保護対象と同じ場所に置くと自己参照になる。** 保護ルールは、ループが編集対象と
   しているスコープより上位に置く必要がある。

したがって多層で組む。上位スコープの権限拒否 → 実行前に止めるフック → OS レベルの隔離
（ファイル単位の拒否はスクリプト経由の読み書きまでは止められないことがある）→ レビュー側の関門。

## 10. 人間をどこに置くか

| 判断 | 誰が |
|---|---|
| 何が問題か | ループ（証拠と発生回数つきで） |
| どう直しうるか | ループ（複数案を並行して） |
| 局所的で可逆な変更の適用 | ループ |
| 前提を覆す変更の採否 | 人間 |
| 評価の定義・指標・ケースの変更 | 人間（最上位ゲート） |
| 権限・hooks・外部通信の変更 | 人間 |

ゲートを機能させるための3点：**評価に関する変更は最上位に置く**、
**提案数に上限を設ける**（承認待ちが溜まると中身を見ずに承認するようになる）、
**無反応は却下として扱う**（放置された提案が黙って適用される経路を作らない）。
承認依頼は1枚に収める。読まれない承認はゲートではない。

前提破壊枠を「提案はループ、採否は人間」にしているのは、それが定義上いちばん大きな設計変更であり、
自動適用の失敗コストがいちばん高いため。自動化率を上げることは目標ではない。
そして却下した提案も消さない。**一度負けた候補を在庫として持ち続けることが、局所最適から抜ける唯一の手段**だから。
