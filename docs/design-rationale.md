# 設計の根拠

2つのプロンプトに書かれた制約が、それぞれどの失敗モードを防いでいるかの対応表。
プロンプトを書き換えるときは、この表を見て「何を外そうとしているのか」を確認すること。

## 1. 前提となる問題

自己改善エージェントが最初の前提を覆せない理由は、能力ではなく**探索構造**にある。

| 構造上の性質 | 帰結 |
|---|---|
| 最初の要件定義がアンカーになる | 以降の改善はすべてその周辺で起きる |
| 自己反省が同じモデル・同じ文脈で行われる | 同じ推論経路をなぞり、反省の射程が広がらない |
| 「いま一番良い1本」を単一スコアで磨く | グローバルベストの近傍しか探索されない |
| 単調改善のルール | 一度スコアを下げる方向の一歩が構造的に禁止される |

脱出は3方向。**複数候補の並行改善**（パレート選択）、**アーカイブと系統による踏み石の保存**、
**多様性を評価に組み込むこと**。プロンプト2の P1〜P5 はこの3つの直接の実装指示にあたる。

## 2. なぜ観測と変更を分離したか

MCP サーバー（プロンプト1）にはハーネスを変更する機能を持たせず、
自己改善ループ（プロンプト2）には観測ロジックを持たせない。

分離自体が安全機構である。同じ主体が「測る」と「良く見せるために変える」の両方を持つと、
指標を上げる最短経路は「測り方を変えること」になる。
プロンプト1 の非目標に「ハーネスを変更する機能を持たせない」を、
プロンプト2 の P9 に「提案する者と評価する者を分ける」を置いているのは同じ理由。

## 3. 制約 → 防いでいる失敗モード

### プロンプト1（MCP サーバー）

| 制約 | 防いでいる失敗 |
|---|---|
| C1 コンテキスト経済性 | 生トランスクリプトの流し込みで、分析する側の文脈が1回の呼び出しで溶ける |
| C2 証拠の添付 | 「よくエラーが起きている気がする」という印象論の上に改善が積み上がる |
| C3 決定性 | 評価関数として使えない（呼ぶたびに結論が揺れると前後比較が成立しない） |
| C4 読み取り専用・ローカル完結 | 認証情報や非公開コードの外部流出、証拠そのものの破壊 |
| C5 正直さ | 欠測をもっともらしい数字で埋め、ループが嘘の上に改善を積む |
| C6 安定した識別子 | 「あのとき見つけた問題はまだ起きているか」を追跡できない |
| C7 規模への耐性 | セッション増加でループが回らなくなり、運用が止まる |

「まず実物を調べる」を第1節に置いたのは、記録に存在しないデータを前提にした分析軸を作らせないため。
分析軸はデータから逆算する。

### プロンプト2（自己改善ループ）

| 原則 | 防いでいる失敗 |
|---|---|
| P1 丘登り禁止 | 局所最適への直行 |
| P2 パレート保持 | 総合1位への一元化で探索が死ぬ |
| P3 アーカイブと系統 | 踏み石の喪失。いま劣る枝が数世代先で最良になる可能性を潰す |
| P4 多様性を評価に | 全候補が同じ前提上の微調整になる（見かけ上は動いているが探索していない） |
| P5 前提破壊枠の義務化 | 指標が良好なときほど局所最適に居座る。良好さが探索を止める |
| P6 前提台帳 | 書かれていない前提は覆せない |
| P7 テキストの反省信号 | スカラーからは改善の方向が読めない |
| P8 証拠なき提案の却下 | 一般論でハーネスが単調に膨らむ |
| P9 提案者と評価者の分離 | 自分の点数のつけ方を自分で変える |
| P10 削除も改善 | ルールが増え、遵守率が下がり、ハーネスが機能しなくなる |
| P11 可逆性 | 悪化に気づいたときに戻せない |
| P12 正直な報告 | 成果の過大報告。ここが壊れるとループ全体が無価値になる |

### 反ゴドハートの構造

- 指標は必ず複数、かつトレードオフ関係にあるものを混ぜる（速さ ↔ やり直しの少なさ）
- 各指標について「これだけを最大化したら何が起きるか」を先に書き、対の指標を置く
- 隠しケースを持ち、公開ケースとの乖離で過学習を検出する
- 観測を減らす変更、ケースを消す変更、失敗を「対象外」に再分類する変更を構造的に禁止する

最後の3つは、指標を上げる最短経路が「良くすること」ではなく「測るのをやめること」になる
典型的な抜け穴を塞いでいる。

## 4. 人間をどこに置くか

| 判断 | 誰が |
|---|---|
| 何が問題か | ループ（証拠つきで） |
| どう直しうるか | ループ（複数案を並行して） |
| 局所的で可逆な変更の適用 | ループ |
| 前提を覆す変更の採否 | 人間 |
| 評価の定義・指標・ケースの変更 | 人間 |
| 権限・hooks・外部通信の変更 | 人間 |

前提破壊枠を「提案はループ、採否は人間」にしているのは、
それが定義上いちばん大きな設計変更であり、かつ自動適用の失敗コストがいちばん高いため。
自動化率を上げることは目標ではない。
