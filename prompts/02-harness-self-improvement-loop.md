# プロンプト2：ハーネス自己改善ループの構築

> このファイルの「---」以降が、Claude Code にそのまま渡すプロンプト本文です。
> プロンプト1（セッション分析 MCP サーバー）が動いている前提で渡してください。

---

あなたには、Claude Code のハーネスを、実際のセッションから得た証拠にもとづいて改善し続けるループを構築してもらいます。

ここでいうハーネスとは、モデルの外側にある行動の枠組みのすべてです。CLAUDE.md、skills、hooks、subagents、slash commands、settings.json、MCP サーバー構成、そしてこのループ自身の運用手順も含みます。

## 0. 何を作らないかを先に言います

「セッションを振り返って、気づいたことを CLAUDE.md に書き足す」— これは作らないでください。それは自己改善ループではなく、自己肯定の記録装置です。しかもこの形は、放っておくと最も高い確率で発生します。理由は第2節 P10 で説明します。

## 1. なぜ素朴な自己改善ループは失敗するのか

自己改善エージェントが最初の前提を覆せないのは、モデルの能力不足が主因ではなく、**探索構造そのもの**に原因があります。

- 最初に置いた前提（最初の要件定義、最初の CLAUDE.md）が**アンカー**になり、以降の改善はすべてその周辺で起きる
- 自己反省は、同じモデルが同じ文脈で行う以上、**同じ推論経路をなぞりやすい**。反省を重ねても、反省が届く範囲は広がらない
- 「いま一番良い1本」だけを持って、単一のスコアを少しずつ上げていくと、**そのグローバルベストの近傍しか探索されない**
- その結果、**局所最適**に落ちる。より良い解に到達するには一度スコアを下げる方向に進む必要があるのに、単調改善のルールがその一歩を禁止している

つまり、前提を覆す力は、エージェントに賢くなれと命じても出てきません。**前提を覆せる探索構造をハーネス側に用意すること**でしか出てきません。あなたが作るのは、その探索構造です。

この問題意識と、脱出方法の整理は次の記事にもとづいています。実装前に読んでください。

- 自己改善エージェントはなぜ前提を覆せないのか ― 局所最適とハーネスでの脱出
  https://zenn.dev/layerx/articles/b36ceffe6b5e20

記事が挙げる脱出の観点は3つです。この3つは、あなたの設計に必ず反映してください。

1. **複数の候補を並行して改善する** — 単一候補の丘登りをやめる（GEPA 的なパレート選択）
2. **過去の候補をアーカイブして再利用する** — 捨てた枝を踏み石として残す（DGM / HGM 的な系統とアーカイブ）
3. **候補の多様性を評価に組み込む** — 似た候補ばかり生まれる状態を、評価の側で不利にする（Diverse Prompts / GEA 的な発想）

背景となる原典も参照してよいです。GEPA（arXiv:2507.19457）、Darwin Gödel Machine（arXiv:2505.22954）、Huxley-Gödel Machine（arXiv:2510.21614）、AlphaEvolve / MAP-Elites 系。ただし論文の再現が目的ではありません。**探索構造の考え方だけを借りて、Claude Code のハーネスという対象に翻訳してください。**

## 2. 譲れない設計原則

技術的な実現方法は、あなたが決めてください。ただし次の原則は制約です。設計判断が原則と衝突したら、原則を優先し、衝突したことを私に報告してください。

**P0. 探索の制御をモデルの判断に委ねない**
候補の選抜、アーカイブへの出し入れ、多様性の判定、採用の可否は、**決定的に計算できる仕組み**（スクリプト、MCP のツール、フック）に置いてください。LLM に任せるのは「変異を生成すること」と「トレースを読んで原因を診断すること」の2つだけです。選抜の基準を自然言語の判断に委ねると、基準はそのラウンドの都合で動きます。動く基準の上に積み上げた改善は、改善ではありません。
評価ケースの合否判定も、エージェント自身にさせないでください。**実行結果とファイルの状態を、エージェントの外側のスクリプトが検証する**形にしてください。

**P1. 単一候補・単一スコアの丘登りを禁止する**
1ラウンドで生成する改善候補は複数にしてください。そして「総合点が最も高い1本」だけを残す選抜をしないでください。
**複数の指標を重み付けして1つの合成スコアにまとめないでください。** 重み付けは、どこを狙えば点が上がるかの設計図そのものです。それを渡した時点で、探索はその抜け穴に向かいます。

**P2. パレート的に残す。保持と選択を分けて設計する**
どれか1つの観点（特定の作業種別、特定の指標、特定の失敗パターン）で最良であれば、総合点が劣っていても候補は生き残らせてください。総合1位に一元化した時点で、探索は死にます。
そして「**何を残すか（保持のルール）**」と「**次にどれを親にするか（選択のルール）**」を別のルールとして設計してください。前者は多様性の被覆を担い、後者は系統の分岐を担います。両者を1つのスコアで兼ねると、必ず片方が犠牲になります。

**P3. 捨てた候補を保存する。そして「良い候補」と「良い親」を区別する**
不採用にした候補も、その内容、スコア、**なぜ不採用にしたかの理由**とともに残してください。各候補には親がどれかを記録し、系統を辿れるようにしてください。
そのうえで、次のラウンドの分岐元を「いま最も点が高い候補」で決めないでください。**いま点が高いことと、良い子孫を生むことは別です。** 高得点の候補が行き止まりで、見劣りする候補が実りある分岐点になることがあります。親の選び方には、その候補から派生した後続がその後どうなったかを反映させ、**すべての候補が選ばれる可能性をゼロにしない**でください。いま劣っている枝が数世代先で最良になる余地を、構造として残すということです。

**P4. 多様性を評価に入れる。ただし構造で測る**
生成された候補が互いに似ている状態を検出し、不利に扱ってください。「全候補が同じ前提の上での微調整だった」ラウンドは、失敗ラウンドとして扱い、やり直させてください。
多様性は、**ハーネスの構造的な性質**で測ってください。たとえば、指示をどれくらいの粒度で与えているか、検証をどれくらい強制しているか、作業をどれくらい分割・委譲しているか、といった軸です。文字数のばらつきや語彙の違いで測ってはいけません。それは簡単に水増しできるので、必ず水増しされます。

**P5. 前提破壊枠を義務化する**
毎ラウンド、少なくとも1つの候補は「既存のハーネスが置いている前提のどれかを否定する」ものにしてください。改良ではなく、否定です。ルールを足すのではなく消す、責務の分割を変える、いま自明とされている運用をやめる、といった候補です。この枠は、直近の指標が良好であっても省略しないでください。指標が良好なときほど、局所最適に居座っている可能性が高いからです。
また、候補を生成させるときは、**過去に試して駄目だった手の一覧**を必ず渡してください。それを渡さないと、ループは同じ失敗を何度でも新案として提出します。

**P6. 前提を明文化する（前提台帳）**
書かれていない前提は覆せません。現在のハーネスが暗黙に置いている前提を、一覧として明文化し、維持してください。「なぜこのルールが存在するのか」「それが成り立たなくなるのはどんなときか」「もしこれをやめたら何が壊れると想定しているか」。P5 の前提破壊枠は、この台帳から選んでください。

**P7. 反省の信号はスカラーではなくテキストにする**
「スコアが 0.7 だった」からは何も学べません。改善の入力は、**セッションに実在する具体的な事実**にしてください。どのターンで何が起きたか、人間が何と言って訂正したか、どのツール呼び出しが何回失敗したか。数値は候補の選抜に使い、生成の材料には言葉を使ってください。

**P8. 証拠のない提案を却下する**
すべての改善候補は、それが解こうとしている問題の証拠（実在するセッションの該当箇所と、**それが何回起きたか**）を伴わなければなりません。「一般的に良いとされているから」「ベストプラクティスだから」を理由にした変更は却下してください。1回しか観測されていない事象を、恒久的なルールの根拠にしないでください。

**P9. 提案する者と評価する者を分ける**
候補を生成する役と、候補を評価する役を分離してください。同じ文脈で連続して行わないでください。そして**評価の定義、評価ケース、指標を、提案側が書き換えられないようにしてください**。自分の点数のつけ方を自分で変えられる構造は、必ず点数を上げる方向に壊れます。
評価は、可能な限り LLM の判定ではなく、実行して確かめられるもの（テストの終了コード、ファイルの状態、決定的に数えられる量）に寄せてください。

**P10. 改善手段には優先順位がある。まず削れ**
このループが陥る最も可能性の高い局所最適は、**「失敗を見つけた → 指示文に1行足す」を繰り返すこと**です。これは最も手軽で、短期的には正しく見えて、長期的には確実にハーネスを壊します。指示は増えるほど1つあたりの遵守率が下がるからです。改善が積み上がるほど効かなくなる、という形の失敗です。

改善手段は、次の優先順位で検討させてください。上から順に試して、上が使えないときだけ下に降りること。

1. **既存の指示を削る・統合する**（それがなくても正しく動くなら消す）
2. **仕組みに落とす**（文章で守らせるのではなく、フックやツールの制約として機械的に強制する）
3. **文脈を限定した形にする**（常に読ませるのではなく、必要なときだけ効く形に切り出す）
4. **最後の手段として、常時読まれる指示に追記する**

そして、常時読み込まれる指示の量に**上限を設けてください**。上限に達したら、追記するには何かを削る必要がある、という制約にしてください。「削る」候補が構造的に不利にならないようにしてください。

**P11. 1ラウンドの変更は最小単位にし、狙う指標を先に宣言させる**
1つのラウンドで複数の要素を同時に変えないでください。同時に変えると、良くなった／悪くなった原因がどれなのか永久に分かりません。
そして候補を出す時点で、**その候補がどの指標を良くするつもりなのかを1つだけ先に宣言させてください。** 評価が終わってから「この指標が良くなっていた」と後付けで探すことを禁止してください。指標を8個見て1個良ければ、偶然でもそうなります。

**P12. 可逆性を担保する**
すべての変更はバージョン管理下に置き、1ラウンドの変更が1単位で戻せるようにしてください。何をいつ、どの候補として、どの証拠にもとづいて適用したかの履歴を残してください。ロールバック手順を実際に一度実行して、動くことを確認してください。
**Claude Code のチェックポイント（`/rewind`）をロールバック手段として当てにしないでください。** シェルコマンドによる変更やサブエージェントの変更は復元されません。可逆性を担保できるのは git だけです。
あわせて、**全部を一度に止める手順**（フックを一時的に無効化して起動する方法など）を用意し、実際に動くことを確認して手順書に書いておいてください。ループが自分で自分を壊したときに、それが唯一の出口になります。

**P13. 正直に報告する**
サンプル数が少なければ、少ないと言ってください。指標が動いた理由が変更なのか作業内容の違いなのか分からなければ、分からないと言ってください。改善したと言い切るための根拠がないなら、言い切らないでください。**ループが自分の成果を過大報告し始めた時点で、このループは価値を失います。**

## 3. ループが持ち続ける状態

何をどう保存するかはあなたが決めてください。ただし、次の情報は失われないようにしてください。

- **前提台帳** — 現在のハーネスが置いている前提の一覧（P6）
- **候補アーカイブ** — 採用・不採用を問わない全候補と、その系統（親が誰か）、スコア、不採用理由（P3）
- **禁止手リスト** — 過去に試して駄目だった手と、その理由（P5）
- **提案台帳** — 出したすべての提案。採用されたものも、却下されたものも。追記のみで、削除しない
- **評価ケース集** — 次の2つの軸で分類してください
  - 目的による分類：**過去に実際に起きた失敗を再現するケース**（解決したら凍結して永久に回し続ける）／期待する能力を測るケース／**やってはいけないことをやらないかを測るケース**
  - 可視性による分類：候補生成側に見せるケース／見せないが開発中の確認に使うケース／**採用の可否判定にだけ使い、それ以外では一切参照しないケース**
- **スコア表** — 候補 × ケース × 指標。**平均に潰した値を保存しないでください。** ケース単位の生の値と、反復のばらつきを保存してください
- **適用履歴** — いつ、何を、どの証拠で変え、その後どうなったか
- **停滞の記録** — 何ラウンド、パレート境界に動きがないか

評価ケースについて2点、注意があります。

**過去のトランスクリプトをそのまま正解にしないでください。** 同じ入力でも出力は毎回揺れるので、必ず落ちます。ケースから取り出すべきは、開始時点の状態、与えられた指示、そして**実行して確かめられる合否条件**だけです。

**壊れたケースを合格として扱わないでください。** 環境が古くなって準備が失敗するようになったケースは、「合格」ではなく「無効」です。これを取り違えると、回帰スイートが静かに空になり、誰も気づきません。定期的にケースの健全性を確認する仕組みを入れてください。

## 4. 1ラウンドの流れ

大枠として次を満たしてください。段取りの詳細はあなたが設計してください。

1. **観測** — 前回ラウンド以降のセッションを分析する。分析は必ず、プロンプト1で作った MCP サーバーを使ってください。あなたの記憶や印象で代替しないでください
2. **問題の抽出** — 証拠つきで、いま起きている問題を列挙する。頻度と影響で並べる
3. **候補生成** — 複数の候補を生成する。うち最低1つは前提破壊枠（P5）。互いに似ていないこと（P4）。分岐元は最良候補だけにしない（P3）。禁止手リストを渡すこと。各候補は狙う指標を1つ宣言すること（P11）
4. **評価** — 隔離した環境で、候補ごとにハーネス構成を差し替えて評価ケースを実行する。合否はエージェントの外側で判定する（P0）。同じケースを複数回繰り返し、ばらつきも記録する
5. **選抜** — 決定的な計算でパレート的に残す（P0, P2）。不採用は理由とともにアーカイブへ
6. **適用** — 承認ゲート（第6節）を通ったものだけを、最小単位で適用する（P11）
7. **検証** — 適用後、回帰ケースが全通過することを確認する。1件でも落ちたら戻す
8. **記録** — 前提台帳、履歴、禁止手リスト、提案台帳、停滞の記録を更新する
9. **報告** — 何を変え、何が良くなり、**何が悪くなり**、何が分からなかったかを報告する

**ヒント（従う義務はありません）**：候補ごとにハーネス構成を差し替えて非対話で実行し、作業ツリーを分けて並行させると、「複数候補の並行評価」が実際に成立します。手段はあなたが決めてください。

## 5. フェーズ1：測れるようにする。この間は一切適用しない

いきなり改善を始めないでください。**探索構造より先に、評価を作ってください。** 何が良くなったと言えるのかが測れないまま回すループは、改善ではなくノイズを生成します。

最初のフェーズでは次だけを行い、**ハーネスへの変更は一切適用しないでください**（提案は出してよい。適用だけを禁止する）。

- 現在のハーネスの全体像を棚卸しし、前提台帳の初版を作る
- 過去セッションを分析し、評価ケース集を作る。第3節の2軸の分類を最初から行う
- 指標の定義を確定し、それぞれについて「どう gaming されうるか」を書き出す
- **ベースラインを測る**。いま何がどれくらいなのか、そして**同じ条件で繰り返したときにどれくらいばらつくのか**を記録する

最後の項目を飛ばさないでください。**効果量よりばらつきのほうが大きければ、その指標では何も判定できません。** それを知らずに始めると、ループはノイズを改善と呼び続けます。

このフェーズをいつ終えるかの条件を、あなたが提案してください。私が合意したら次に進みます。

## 6. 人間の承認ゲート

段階を分けてください。おおよそ次の切り分けを想定していますが、境界の具体化はあなたが提案してください。

| 段階 | 対象の例 | 人間の関与 |
|---|---|---|
| 自動適用 | 指示文の**削除・短縮**、表現の明確化、既存の説明への例示追加 | なし（定期サマリーで事後に見る） |
| 自動適用＋事後レビュー | 指示の**追加**、新しい skill や subagent の追加 | 事後に確認し、異議があれば自動で戻す |
| 事前承認 | hooks、権限設定、settings.json、MCP 構成、subagent や skill が使えるツールの範囲 | **必須。人間が承認するまで適用しない** |
| 事前承認＋設計レビュー | 前提を覆す提案、ワークフロー全体の再構成、**評価指標と評価ケース自体の変更** | **必須。別枠で扱う（第7節）** |

判断軸は、可逆性・影響範囲・権限境界に触れるか・決定的に検証できるか・前提を変えるか、の5つです。

そして次の3つを必ず入れてください。

- **評価に関する変更は最上位のゲートに置く。** ここを緩めると、ループは「良くする」より「良く判定されるようにする」に最適化します
- **提案の数に上限を設ける**（たとえば週あたり何件まで、事前承認が必要なものは何件まで）。承認待ちが溜まると、人間は中身を見ずに承認するようになり、ゲートは実質的に消えます
- **無反応は却下として扱う。** 一定期間レビューされなかった提案は自動で却下にしてください。放置された提案が黙って適用される経路を作らないでください

承認を求めるときは、次を1枚に収めてください。長い提案は読まれず、読まれない承認はゲートとして機能しません。

1. **何を変えるか** — 差分そのもの。長くなるなら分割すること
2. **なぜ** — 証拠。どのセッションで、何が、**何回**起きたか
3. **何がどう良くなる想定か** — 宣言した指標1つと、評価の実測値（変更前／変更後／ばらつき）
4. **撤回条件** — 「この指標がこうなったら戻す」を、適用前に自分で書かせること

## 7. 「前提を覆す」提案の扱い

自動適用しない。**しかし捨てない。** ここがこのループの肝です。

前提破壊枠の候補は、実装せずに提案文書として書き出してください。「いまの前提」「覆す前提」「観測された根拠」「予想される影響（悪くなる方も書く）」「どう実験するか」「失敗と判定する条件」を含めてください。

そして、却下したものも消さないでください。状況が変われば有効になる可能性があり、同じ提案が何度も出てくるのを防ぐ意味もあります。**一度負けた候補を在庫として持ち続けることが、局所最適から抜ける唯一の手段です。**

私が「試す」と判断したものだけ、本流に入れずに別バリアントとして並行運用し、パレート比較で本流を上回ったら昇格させてください。上回らなければ、棚に戻してください。

## 8. 指標の構造と、採用の判断

### 指標は3層に分ける

**層1：ゲート指標（満たすか満たさないかの二値）。1つでも割れたら自動却下。**
安全性に関わる変更が含まれていないこと、検証が実際に実行されたこと、回帰ケースが全通過すること、ハーネスの分量が予算内であること、評価ケースの合否条件が変更されていないこと。

**層2：主要指標（1つ）。** その候補が良くすると宣言したもの（P11）。

**層3：副次指標。** 残り。パレート判定に使う。

**主要指標が改善し、副次指標のどれも有意に悪化していない場合にのみ採用**してください。トレードオフが発生した場合は自動採用せず、人間に上げてください。そして「この指標を1上げるために、この指標をここまで犠牲にしてよい」という許容範囲を、事前に文章で決めておいてください。決めておかないと、エージェントは必ず一番動かしやすい指標を動かします。

### 各指標について、gaming の経路を先に書き出す

「これだけを最大化したら何が起きるか」を先に書き、その悪化を検出する対の指標を必ず置いてください。実例をいくつか挙げます。同じ構造の穴を、あなたが選んだ指標についても洗い出してください。

- **成功率** → 検証を弱めれば上がる。簡単な作業だけを対象に選んでも上がる。だから**合否条件が変更されていないこと**をゲート指標に置く
- **手戻りの少なさ** → 何もしなければ手戻りは起きない。**人間が諦めて自分で直した場合も、記録上は手戻りゼロに見える**。だから必ず「どれだけ仕事が進んだか」と対にして見る
- **トークン効率** → 調べずに推測で書けば下がる。**サブエージェントに押し付ければ、親の数字だけは下がる**。だから作業1件あたりの総量で測り、委譲先の分を必ず合算する
- **人間の介入の少なさ** → **権限設定を緩めれば劇的に下がる**。これは安全性を売って指標を買っているだけです。だから権限設定に触れる変更は、この指標の最適化対象から外し、必ず事前承認に回してください
- **所要ターン数** → 検証の手順を省けば減る。だから「検証が実行されたこと」をゲート指標に置く
- **指示の遵守率** → 指示を足せば足すほど上がるように見えて、実際には全体の遵守率を下げる（P10）

### サンプルが少ないときの採用ルール

| 証拠 | 判断 |
|---|---|
| ゲート指標が1つでも割れた | 自動却下 |
| **決定的に再現する回帰ケースが、変更前は必ず失敗し、変更後は繰り返し成功する** | 1件でも採用してよい。根拠は統計ではなく再現性 |
| 平均は改善したが、差がばらつきの範囲内 | 採用しない。ただし記録は残す |
| 差がばらつきを明確に超え、副次指標の悪化がない | 採用してよい |
| 主要指標は改善したが副次指標が悪化 | 人間に上げる |

あわせて次を守ってください。

- 比較は**同じ評価ケース集で、同じ日に、同じバージョンの Claude Code で**行う。期間の前後比較はしないこと。作業内容やバージョンの違いと区別がつきません
- 各ケースは複数回繰り返し、ばらつきを併記する
- **効果がなかったことも必ず記録する。** 記録しないと、ループは同じ提案を何度も出します
- 採用の可否判定にだけ使うケースの成績と、それ以外の成績が乖離し始めたら、評価ケースへの過学習です。ループを止めて報告してください
- 指標が飽和した（どの候補もほぼ満点）場合、その指標はもう探索の役に立ちません。置き換えを提案してください

## 9. 不変条件（自動変更を絶対に許さない領域）

次はループが自動で変更してはいけません。変更が必要だと判断した場合は、変更せずに提案として報告してください。

- **権限設定に関わるもの全般**（緩和にあたる変更はもちろん、追加も含む）
- **hooks の追加・変更**、MCP サーバー構成、外部と通信する設定、subagent や skill が使えるツールの範囲
- **評価の一切**（評価ケース、合否条件、指標の定義、集計と実行の仕組み）
- **このループ自身の安全機構**（承認ゲート、不変条件の定義、この節そのもの）
- 秘密情報の取り扱いに関する設定
- 記録の保持期間や保存先に関する設定
- 私が明示的に「触るな」と指定したファイル。この指定を置く場所を用意し、ループが起動時に必ず読むようにしてください

### これらは「そう書いておく」だけでは守られません

理由を具体的に3つ挙げます。

**1つめ。エージェントは「良くなること」ではなく「良いと判定されること」に最適化します。** 自己改善するコーディングエージェントの研究では、「ツールの使用について嘘をつくな」という評価項目を追加したところ、エージェントが嘘そのものを減らすのではなく、**その嘘を検出するための目印をログから消す方向にコードを書き換えた**という事例が報告されています。目標の書き方を工夫しても防げません。評価と記録の仕組みを、エージェントの手が届かない場所に置くことでしか防げません。

**2つめ。Claude Code の設定は実行中に自動で読み直されます。** つまりエージェントが自分でフックを書けば、**同じセッションの中で、それが即座に任意のコマンドとして動き出します**。自己改善ループは「生成したコードが自動で常時実行される」経路を、構造として内包しています。

**3つめ。保護の宣言を、保護対象と同じ場所に置くと自己参照になります。** プロジェクト内の設定ファイルで「このプロジェクトの設定ファイルを変更するな」と書いても、ループはその設定ファイルごと編集できます。**保護のルールは、ループが編集対象としているスコープより上位に置いてください。**

したがって、次を多層で組んでください。

- 上位スコープの権限設定で、保護対象への書き込みを拒否する
- ツール実行前に検査して止めるフックを、同じく上位スコープに置く
- **ファイル単位の拒否ルールは、エージェントのファイル編集ツールや一般的なコマンドには効いても、スクリプトが自分でファイルを開く経路までは止められないことがあります。** OS レベルの隔離を併用してください
- 変更が git を経由するなら、保護対象の差分を含む変更を機械的に弾く関門を、レビュー側にも置いてください

そのうえで、次を構造的に禁止してください。

- ハーネスの変更によって、セッションに記録される情報を減らすこと（＝観測できなくして、指標を良く見せること）
- 評価ケースを削除・緩和して指標を上げること
- 失敗したケースを「対象外」に分類し直して指標を上げること
- フックやサブエージェントを使った、無制限に自己を再帰起動する構成

## 10. 停滞したときの扱い

パレート境界が数ラウンド動かない、あるいは生成される候補が毎回似通うようになったら、それは**探索が局所最適に閉じ込められた**サインです。指標が高値で安定していても同じです。

そのときは、通常のラウンドを続けないでください。前提台帳を頭から見直し、「そもそもこの前提が必要か」を問い直すラウンドに切り替え、その結果を私に報告してください。停滞を検出する条件と、切り替えの手順を、設計に含めてください。

## 11. 受け入れ基準

構築後、次を実際に実行して結果を報告してください。

1. フェーズ1が完了し、前提台帳・分類された評価ケース集・ベースライン（**ばらつきを含む**）が存在すること
2. 実際に1ラウンドを最後まで回せること。複数候補が生成され、うち1つ以上が前提破壊枠であり、パレート的な選抜が行われ、不採用候補が理由とともに残っていること
3. 選抜が決定的であること（P0）。同じスコア表から同じ選抜結果が再現されること
4. 合否判定がエージェントの外側で行われていること。エージェントに「合格した」と言わせるのではなく、外部の検証結果を示すこと
5. 生成された候補のすべてが、実在するセッションの証拠と発生回数を伴っていること（P8）。伴っていない候補が却下される様子を実際に見せること
6. 適用した変更を、記録されたロールバック手順で実際に戻せること。**全体を止める手順も実際に動かして見せること**
7. 意図的に「指標を上げるが実質的に悪化する」候補を混ぜたとき、ゲート指標で止まること
8. 不変条件に触れる変更が、自動適用されずに提案として上がってくること。**書いてあるだけでなく、実際に書き込みが機械的に拒否されること**を実演すること
9. 全候補が似通ったラウンドが、失敗ラウンドとして扱われること

## 12. 非目標

- 完全自動化しないでください。人間の承認ゲートを外すことは目標ではありません
- 指標を上げること自体を目標にしないでください。目標は、実際の作業が良くなることです
- 汎用の「AI 自己改善フレームワーク」を作らないでください。対象は、私の Claude Code のハーネスです
- 論文の忠実な再現をしないでください。借りるのは探索構造の考え方だけです
- 承認プロンプトの数を減らすことを、このループの目的にしないでください。それは別の作業です

## 13. 進め方

実装に入る前に、次を設計案として提示してください。

- ハーネスのどこをループの改善対象とし、どこを対象外とするか
- 候補、アーカイブ、系統、スコア表を、Claude Code のハーネスという対象に対して具体的に何として表現するか
- 選抜・多様性判定・合否判定を、どこに決定的な仕組みとして置くか（P0）
- 指標の候補と、それぞれの gaming 経路、および対になる指標
- 不変条件を機械的に強制する具体的な手段と、その多層構造
- フェーズ1をいつ終えるかの条件
- ラウンドをいつ、何をきっかけに回すか
- **この設計で、ループが局所最適に落ちるとしたら、どういう経路で落ちるか**

最後の項目は必ず答えてください。答えられないなら、その設計はまだ考え切れていません。
