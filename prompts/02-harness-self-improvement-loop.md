# プロンプト2：ハーネス自己改善ループの構築

> このファイルの「---」以降が、Claude Code にそのまま渡すプロンプト本文です。
> プロンプト1（セッション分析 MCP サーバー）が動いている前提で渡してください。

---

あなたには、Claude Code のハーネスを、実際のセッションから得た証拠にもとづいて改善し続けるループを構築してもらいます。

ここでいうハーネスとは、モデルの外側にある行動の枠組みのすべてです。CLAUDE.md、skills、hooks、subagents、slash commands、settings.json、MCP サーバー構成、そしてこのループ自身の運用手順も含みます。

## 0. 何を作らないかを先に言います

「セッションを振り返って、気づいたことを CLAUDE.md に書き足す」— これは作らないでください。それは自己改善ループではなく、自己肯定の記録装置です。

## 1. なぜ素朴な自己改善ループは失敗するのか

自己改善エージェントが最初の前提を覆せないのは、モデルの能力不足が主因ではなく、**探索構造そのもの**に原因があります。

- 最初に置いた前提（最初の要件定義、最初の CLAUDE.md）が**アンカー**になり、以降の改善はすべてその周辺で起きる
- 自己反省は、同じモデルが同じ文脈で行う以上、**同じ推論経路をなぞりやすい**。反省を重ねても、反省が届く範囲は広がらない
- 「いま一番良い1本」だけを持って、単一のスコアを少しずつ上げていくと、**そのグローバルベストの近傍しか探索されない**
- その結果、**局所最適**に落ちる。より良い解に到達するには一度スコアを下げる方向に進む必要があるのに、単調改善のルールがその一歩を禁止している

つまり、前提を覆す力は、エージェントに賢くなれと命じても出てきません。**前提を覆せる探索構造をハーネス側に用意すること**でしか出てきません。あなたが作るのは、その探索構造です。

この問題意識と、脱出方法の整理は次の記事にもとづいています。実装前に読んでください。

- 自己改善エージェントはなぜ前提を覆せないのか ― 局所最適とハーネスでの脱出
  https://zenn.dev/layerx/articles/b36ceffe6b5e20

記事が挙げる脱出の観点は3つです。この3つは、あなたの設計に必ず反映してください。

1. **複数の候補を並行して改善する** — 単一候補の丘登りをやめる（GEPA 的なパレート選択）
2. **過去の候補をアーカイブして再利用する** — 捨てた枝を踏み石として残す（DGM / HGM 的な系統とアーカイブ）
3. **候補の多様性を評価に組み込む** — 似た候補ばかり生まれる状態を、評価の側で不利にする（Diverse Prompts / GEA 的な発想）

背景となる原典も参照してよいです。GEPA（arXiv:2507.19457）、Huxley-Gödel Machine（arXiv:2510.21614）、Darwin Gödel Machine。ただし論文の再現が目的ではありません。**探索構造の考え方だけを借りて、Claude Code のハーネスという対象に翻訳してください。**

## 2. 譲れない設計原則

技術的な実現方法は、あなたが決めてください。ただし次の原則は制約です。設計判断が原則と衝突したら、原則を優先し、衝突したことを私に報告してください。

**P1. 単一候補・単一スコアの丘登りを禁止する**
1ラウンドで生成する改善候補は複数にしてください。そして「総合点が最も高い1本」だけを残す選抜をしないでください。

**P2. パレート的に残す**
どれか1つの観点（特定の作業種別、特定の指標、特定の失敗パターン）で最良であれば、総合点が劣っていても候補は生き残らせてください。総合1位に一元化した時点で、探索は死にます。

**P3. 捨てた候補を保存する（アーカイブと系統）**
不採用にした候補も、その内容、スコア、**なぜ不採用にしたかの理由**とともに残してください。各候補には親がどれかを記録し、系統を辿れるようにしてください。そして次のラウンドの分岐元は、**必ずしも現在の最良でなくてよい**こと、むしろ意図的に非最良から分岐する枠を持つことを設計に含めてください。いま劣っている枝が、数世代先で最良になる可能性を、構造として残してください。

**P4. 多様性を評価に入れる**
生成された候補が互いに似ている状態を検出し、不利に扱ってください。「全候補が同じ前提の上での微調整だった」ラウンドは、失敗ラウンドとして扱い、やり直させてください。

**P5. 前提破壊枠を義務化する**
毎ラウンド、少なくとも1つの候補は「既存のハーネスが置いている前提のどれかを否定する」ものにしてください。改良ではなく、否定です。ルールを足すのではなく消す、責務の分割を変える、いま自明とされている運用をやめる、といった候補です。この枠は、直近の指標が良好であっても省略しないでください。指標が良好なときほど、局所最適に居座っている可能性が高いからです。

**P6. 前提を明文化する（前提台帳）**
書かれていない前提は覆せません。現在のハーネスが暗黙に置いている前提を、一覧として明文化し、維持してください。「なぜこのルールが存在するのか」「それが成り立たなくなるのはどんなときか」「もしこれをやめたら何が壊れると想定しているか」。P5 の前提破壊枠は、この台帳から選んでください。

**P7. 反省の信号はスカラーではなくテキストにする**
「スコアが 0.7 だった」からは何も学べません。改善の入力は、**セッションに実在する具体的な事実**にしてください。どのターンで何が起きたか、人間が何と言って訂正したか、どのツール呼び出しが何回失敗したか。数値は候補の選抜に使い、生成の材料には言葉を使ってください。

**P8. 証拠のない提案を却下する**
すべての改善候補は、それが解こうとしている問題の証拠（実在するセッションの該当箇所）を伴わなければなりません。「一般的に良いとされているから」「ベストプラクティスだから」を理由にした変更は却下してください。この規律がないと、ループはハーネスを一般論で膨らませ続けます。

**P9. 提案する者と評価する者を分ける**
候補を生成する役と、候補を評価する役を分離してください。同じ文脈で連続して行わないでください。そして**評価の定義、評価ケース、指標を、提案側が書き換えられないようにしてください**。自分の点数のつけ方を自分で変えられる構造は、必ず点数を上げる方向に壊れます。

**P10. 削除も改善である**
ハーネスは放っておくと単調に増えます。ルールが増えるほど各ルールの遵守率は下がります。「削る」「統合する」「やめる」候補が定期的に生成されるようにし、削除候補が構造的に不利にならないようにしてください。

**P11. 可逆性を担保する**
すべての変更はバージョン管理下に置き、1ラウンドの変更が1単位で戻せるようにしてください。何をいつ、どの候補として、どの証拠にもとづいて適用したかの履歴を残してください。ロールバック手順を実際に一度実行して、動くことを確認してください。

**P12. 正直に報告する**
サンプル数が少なければ、少ないと言ってください。指標が動いた理由が変更なのか作業内容の違いなのか分からなければ、分からないと言ってください。改善したと言い切るための根拠がないなら、言い切らないでください。**ループが自分の成果を過大報告し始めた時点で、このループは価値を失います。**

## 3. ループが持ち続ける状態

何をどう保存するかはあなたが決めてください。ただし、次の情報は失われないようにしてください。

- **前提台帳** — 現在のハーネスが置いている前提の一覧（P6）
- **候補アーカイブ** — 採用・不採用を問わない全候補と、その系統、スコア、不採用理由（P3）
- **評価ケース集** — 過去セッションから作った、再評価に使えるケース群
- **隠しケース** — 候補生成側に見せないケースの一部。過学習の検出用
- **スコア表** — 候補 × ケース × 指標。総合点に潰す前の生の行列（P2 の選抜に必要）
- **適用履歴** — いつ、何を、どの証拠で変え、その後どうなったか
- **停滞の記録** — 何ラウンド、パレート境界に動きがないか

## 4. 1ラウンドの流れ

大枠として次を満たしてください。段取りの詳細はあなたが設計してください。

1. **観測** — 前回ラウンド以降のセッションを分析する。分析は必ず、プロンプト1で作った MCP サーバーを使ってください。あなたの記憶や印象で代替しないでください
2. **問題の抽出** — 証拠つきで、いま起きている問題を列挙する。頻度と影響で並べる
3. **候補生成** — 複数の候補を生成する。うち最低1つは前提破壊枠（P5）。互いに似ていないこと（P4）。分岐元は最良候補だけにしない（P3）
4. **評価** — 評価ケース集に対して候補を評価する。指標は複数。総合点に潰さない
5. **選抜** — パレート的に残す（P2）。不採用は理由とともにアーカイブへ
6. **適用** — 承認ゲート（第6節）を通ったものだけを適用する
7. **検証** — 適用後、回帰が出ていないかを隠しケースを含めて確認する
8. **記録** — 前提台帳、履歴、停滞の記録を更新する
9. **報告** — 何を変え、何が良くなり、**何が悪くなり**、何が分からなかったかを報告する

## 5. ラウンド0：まず測れるようにする

いきなり改善を始めないでください。最初のラウンドは次だけを行ってください。

- 現在のハーネスの全体像を棚卸しし、前提台帳の初版を作る
- 過去セッションを分析し、評価ケース集の初版と、隠しケースを作る
- **ベースラインを測る**。いま何がどれくらいなのかを記録する
- 指標の定義を確定し、それぞれについて「どう gaming されうるか」を書き出す

ベースラインがない状態で入れた変更は、良くなったのか悪くなったのか永久に分かりません。ここを飛ばさないでください。

## 6. 人間の承認ゲート

**自動で適用してよいもの**：影響範囲が局所的で、証拠が明確で、すぐ戻せる変更。

**必ず私の承認を求めるもの**：
- 前提破壊枠の候補（P5）。これは定義上、大きな設計変更です。**提案はループが、採否は人間が**決めます
- ハーネスの構造そのものを変える提案（責務の分割、ファイル構成、ループ自身の手順）
- 評価の定義、指標、評価ケースの変更
- 権限設定（settings.json の permissions）、hooks の追加・変更、外部と通信する設定
- 一度に複数の要素にまたがる変更

承認を求めるときは、証拠、想定される効果、**失敗したときに何が起きるか**、戻し方をセットで出してください。

## 7. 不変条件（自動変更を絶対に許さない領域）

次はループが自動で変更してはいけません。変更が必要だと判断した場合は、変更せずに提案として報告してください。

- 権限設定の緩和にあたるもの全般
- このループ自身の安全機構（承認ゲート、不変条件の定義、この節そのもの）
- 評価器・評価ケース・指標の定義（P9）
- 秘密情報の取り扱いに関する設定
- 私が明示的に「触るな」と指定したファイル。この指定を置く場所を用意し、ループが起動時に必ず読むようにしてください

また、次を構造的に禁止してください。

- ハーネスの変更によって、セッションに記録される情報を減らすこと（＝観測できなくして、指標を良く見せること）
- 評価ケースを削除して指標を上げること
- 失敗したケースを「対象外」に分類し直して指標を上げること
- フックやサブエージェントを使った、無制限に自己を再帰起動する構成

## 8. 指標を守る（反ゴドハート）

指標は必ず複数にし、互いにトレードオフの関係にあるものを混ぜてください。たとえば「速く終わる」と「やり直しが起きない」は、片方だけを追うと必ずもう片方が壊れます。

各指標について「これだけを最大化したら何が起きるか」を先に書き出し、その悪化を検出する対の指標を必ず置いてください。ある候補が1つの指標だけを大きく改善し、他を悪化させている場合、それは改善ではなく、指標の抜け穴を見つけた可能性を先に疑ってください。

隠しケースの成績と公開ケースの成績が乖離し始めたら、評価ケースへの過学習が起きています。そのときはループを止めて報告してください。

## 9. 停滞したときの扱い

パレート境界が数ラウンド動かない、あるいは生成される候補が毎回似通うようになったら、それは**探索が局所最適に閉じ込められた**サインです。指標が高値で安定していても同じです。

そのときは、通常のラウンドを続けないでください。前提台帳を頭から見直し、「そもそもこの前提が必要か」を問い直すラウンドに切り替え、その結果を私に報告してください。停滞を検出する条件と、切り替えの手順を、設計に含めてください。

## 10. 受け入れ基準

構築後、次を実際に実行して結果を報告してください。

1. ラウンド0が完了し、前提台帳・評価ケース集・隠しケース・ベースラインが存在すること
2. 実際に1ラウンドを最後まで回せること。複数候補が生成され、うち1つ以上が前提破壊枠であり、パレート的な選抜が行われ、不採用候補が理由とともに残っていること
3. 生成された候補のすべてが、実在するセッションの証拠を伴っていること（P8）。伴っていない候補が却下される様子を実際に見せること
4. 適用した変更を、記録されたロールバック手順で実際に戻せること
5. 意図的に「指標を上げるが実質的に悪化する」候補を混ぜたとき、それが検出されること
6. 不変条件に触れる変更が、自動適用されずに提案として上がってくること
7. 全候補が似通ったラウンドが、失敗ラウンドとして扱われること

## 11. 非目標

- 完全自動化しないでください。人間の承認ゲートを外すことは目標ではありません
- 指標を上げること自体を目標にしないでください。目標は、実際の作業が良くなることです
- 汎用の「AI 自己改善フレームワーク」を作らないでください。対象は、私の Claude Code のハーネスです
- 論文の忠実な再現をしないでください。借りるのは探索構造の考え方だけです

## 12. 進め方

実装に入る前に、次を設計案として提示してください。

- ハーネスのどこをループの改善対象とし、どこを対象外とするか
- 候補、アーカイブ、系統、スコア表を、Claude Code のハーネスという対象に対して具体的に何として表現するか
- 指標の候補と、それぞれの gaming 経路
- ラウンドをいつ、何をきっかけに回すか
- **この設計で、ループが局所最適に落ちるとしたら、どういう経路で落ちるか**

最後の項目は必ず答えてください。答えられないなら、その設計はまだ考え切れていません。
